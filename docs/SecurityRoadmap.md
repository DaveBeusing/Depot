# Depot Security and Compliance Roadmap

Updated: 2026-09-18

## Purpose

This roadmap records Depot's security, privacy, regulatory and software-assurance engineering state on the path from preview software toward a production-ready ERP. It separates implemented repository controls from deployment, legal, manual and production-release acceptance. It does not itself establish legal compliance or certification.

## Objectives

Depot is engineered toward applicable requirements and principles from the EU Cyber Resilience Act, GDPR/DSGVO, German GoBD, EN 16931/XRechnung electronic invoicing, ISO/IEC 27001, ISO/IEC 27034, ISO/IEC 25010, OWASP ASVS/SAMM, WCAG 2.2 AA / EN 301 549 and enterprise/NIS2-influenced supply-chain requirements.

## Guiding principles

1. Security and privacy by design and by default.
2. Least privilege for users, services and database identities.
3. Finalized business records are immutable where historical integrity requires it.
4. Corrections use traceable reversal/correction transactions rather than destructive edits.
5. Security-relevant actions are auditable.
6. Secrets and credentials are not written to logs or exported unintentionally.
7. Production releases have traceable source, dependencies, build and security status.
8. Vulnerabilities have an owner, severity, remediation target and disclosure process.
9. Backup is incomplete without tested recovery.
10. Compliance evidence should be generated by normal engineering processes wherever practical.
11. Historical financial identity is captured at finalization and is not reconstructed from mutable current master data.
12. Repository implementation, production evidence and legal acceptance remain distinct states.

# Phase 4 - GoBD and business-record integrity

**Status: TECHNICAL IMPLEMENTATION COMPLETE**

Implemented controls include executable business-record classification, immutable finalized states, correction/reversal workflows, stable document identities, chronological Audit reconstruction, actor/timestamp evidence, atomic business/Audit persistence, correction reasons, machine-readable evidence export and migration/recovery integrity rules.

# Release security gate

A production release should not be approved until applicable evidence exists for all of the following:

- [ ] Exact release build and automated tests pass.
- [ ] Security-relevant tests pass.
- [ ] No unresolved critical vulnerability exists in shipped dependencies or code.
- [ ] High vulnerabilities are remediated or explicitly documented and risk-accepted.
- [ ] SBOM and dependency/license evidence are generated.
- [ ] Production executable/package signing is verified where required.
- [ ] Upgrade, repair, rollback and uninstall acceptance is complete for the exact release candidate.
- [ ] Backup and restore evidence exists for supported deployment paths.
- [ ] Interactive accessibility/compatibility acceptance is complete for the exact release candidate.
- [ ] Every advertised electronic-invoice scenario has release-appropriate validation evidence.
- [ ] Release notes include security-relevant changes and known limitations where appropriate.
- [ ] Compliance documentation affected by the release has been reviewed.
