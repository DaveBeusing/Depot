# Depot Security and Compliance Roadmap

## Purpose

This roadmap defines the security, privacy, regulatory and software-assurance work required to move Depot from preview software toward a production-ready inventory and business-operations platform. It is engineering guidance and evidence planning; it does not itself establish legal compliance or certification.

## Objectives

Depot is developed toward applicable requirements and principles from the EU Cyber Resilience Act, GDPR/DSGVO, German GoBD, EN 16931/XRechnung electronic invoicing, ISO/IEC 27001, ISO/IEC 27034, ISO/IEC 25010, OWASP ASVS/SAMM, WCAG 2.2 AA / EN 301 549 and enterprise/NIS2-influenced supply-chain requirements.

## Guiding principles

1. Security and privacy by design and by default.
2. Least privilege for users, services and database identities.
3. Finalized business records are immutable where historical integrity requires it.
4. Corrections use traceable reversal/correction transactions rather than destructive edits.
5. Security-relevant actions are auditable.
6. Secrets and credentials are not written to logs or exported unintentionally.
7. Production releases have traceable source, dependencies, build and security status.
8. Vulnerabilities have an owner, severity, remediation target and disclosure process.
9. Backup is incomplete without tested recovery.
10. Compliance evidence should be generated by normal engineering processes wherever practical.
11. Historical financial identity is captured at finalization and is not reconstructed from mutable current master data.

# Phase 6 - Electronic invoicing readiness

**Status: TECHNICAL IMPLEMENTATION COMPLETE — 2026-08-23**

Implemented technical controls include an EN 16931-oriented semantic invoice model, deterministic XRechnung CII generation, application-level business-term validation, pinned KoSIT representative conformance validation, authoritative Company seller master data, structured Customer Buyer identity, and operational Sales Invoice finalization.

Sales Invoice posting now atomically captures the immutable seller snapshot and Buyer snapshot, generates the XRechnung-oriented CII document, stores the exact issued XML and its SHA-256 fingerprint, and commits the business/audit transition together. Posted invoices expose a verified XML export path that reads the persisted finalization instead of regenerating from current master data. Incomplete identity and unsupported ambiguous tax scenarios fail closed.

- [ ] Validate every advertised tax/profile/channel scenario against the applicable production XRechnung/KoSIT release.

- [ ] Implement and validate a true PDF/A-3 pipeline before claiming ZUGFeRD/Factur-X support.

Primary evidence: `docs/compliance/ELECTRONIC_INVOICING.md`, `INVOICE_FINALIZATION.md`, `COMPANY_MASTER_DATA.md`, `ISSUER_SNAPSHOTS.md`, `PHASE6_STATUS.md`, `ElectronicInvoice`, `ElectronicInvoiceService`, `SalesInvoiceFinalizationService`, finalization/conformance tests and `.github/workflows/electronic-invoice-conformance.yml`.

# Release security gate

A production release should not be approved until applicable evidence exists for all of the following:

- [ ] Release build and automated tests pass.
- [ ] Security-relevant tests pass.
- [ ] No unresolved critical vulnerability exists in shipped dependencies or code.
- [ ] High vulnerabilities are remediated or explicitly documented and risk-accepted.
- [ ] SBOM generated and dependency/license review completed.
- [ ] Executable/package signing verified.
- [ ] Upgrade and rollback tested.
- [ ] Backup and restore tested for supported deployment paths.
- [ ] Phase 7 interactive accessibility/compatibility acceptance completed for the release where applicable.
- [ ] Every advertised electronic-invoice tax/profile/channel scenario has release-specific validation evidence.
- [ ] Release notes include security-relevant changes and known limitations where appropriate.
- [ ] Compliance documentation affected by the release has been reviewed.
