# Depot Security and Compliance Roadmap

## Purpose

This roadmap defines the security, privacy, regulatory, and software-assurance work required to move Depot from a preview application toward a production-ready inventory and business operations platform.

The roadmap is guidance for engineering and release planning. It does not by itself establish legal compliance or certification.

## Objectives

Depot should be developed toward alignment with the following areas where applicable:

- EU Cyber Resilience Act (CRA)
- GDPR / DSGVO
- German GoBD requirements for relevant business records and processes
- EN 16931 based electronic invoicing where invoice exchange is implemented
- ISO/IEC 27001 compatible security controls
- ISO/IEC 27034 application-security practices
- ISO/IEC 25010 software quality characteristics
- OWASP secure-development guidance, including ASVS/SAMM where applicable
- WCAG 2.2 AA / EN 301 549 accessibility principles
- enterprise customer requirements influenced by NIS2 and supply-chain security

## Guiding principles

1. Security by design and by default.
2. Least privilege for users, services, and database identities.
3. Business records become immutable when their workflow requires historical integrity.
4. Corrections use traceable reversal/correction transactions rather than destructive edits.
5. Security-relevant actions are auditable.
6. Secrets and credentials are never written to logs or exported unintentionally.
7. Every production release has a traceable source, dependency set, build, and security status.
8. Vulnerabilities have an owner, severity, remediation target, and disclosure process.
9. Backup is not considered complete without tested recovery.
10. Compliance evidence should be generated by normal engineering processes wherever possible.

# Phase 2 - Security hardening

Target: Before release candidate.

## Authentication and authorization

- [ ] Remove the production default administrator password workflow.
- [ ] Require administrator creation or secure credential initialization on first production start.
- [ ] Enforce an appropriate password policy.
- [ ] Review PBKDF2 parameters against current recommendations before release.
- [ ] Rate-limit or otherwise mitigate repeated authentication attempts where applicable.
- [ ] Verify authorization at service/business boundaries, not only in the UI.
- [ ] Test role union, privilege escalation, administrator override, and creator/approver separation.
- [ ] Evaluate MFA and external identity-provider support for post-1.0 enterprise deployments.

## Secrets and configuration

- [ ] Protect database credentials and other secrets at rest.
- [ ] Define Windows-user/machine behavior for protected configuration.
- [ ] Ensure secrets are redacted from UI errors, logs, telemetry, exports, and crash information.
- [ ] Document secure configuration for SQL Server, MySQL, and MariaDB.
- [ ] Document database least-privilege requirements.
- [ ] Require or strongly recommend encrypted database transport for remote providers.

## Audit and logging

- [ ] Complete the dedicated audit-log viewer.
- [ ] Define security-event categories.
- [ ] Define audit retention and export behavior.
- [ ] Protect audit records from normal application modification/deletion.
- [ ] Record administrator overrides with actor, timestamp, affected object, and reason.
- [ ] Define clock/time-zone handling for audit evidence.
- [ ] Review logs for personal data and commercially sensitive information.

## Backup and recovery

- [ ] Define backup retention policy.
- [ ] Define backup access-control requirements.
- [ ] Evaluate backup encryption.
- [ ] Test clean restore, corrupt backup, interrupted restore, unavailable target, and insufficient-permission scenarios.
- [ ] Perform recovery drills for every supported database provider.
- [ ] Document recovery objectives and operational procedures.

## Release integrity

- [ ] Authenticode-sign production executables and installers/packages.
- [ ] Timestamp signatures.
- [ ] Protect signing credentials outside the source repository.
- [ ] Ensure CI release artifacts correspond to the tagged source revision.
- [ ] Publish hashes for release artifacts where appropriate.

# Phase 3 - GDPR / data protection readiness

Target: Before production use with personal data.

- [ ] Inventory personal-data categories processed by Depot.
- [ ] Document purposes and typical data flows.
- [ ] Identify storage locations including databases, settings, logs, backups, PDFs, and exports.
- [ ] Apply data minimization to master data and logs.
- [ ] Define retention and deletion behavior by record category.
- [ ] Distinguish delete, deactivate, anonymize, archive, and legally retained records.
- [ ] Provide administrator workflows to locate relevant personal data.
- [ ] Define export capability for data-subject requests where applicable.
- [ ] Ensure backup retention is consistent with deletion/retention policy.
- [ ] Document privacy-by-design decisions for major features.
- [ ] Review whether telemetry or remote services are introduced in future releases before enabling them.

# Phase 4 - GoBD and business-record integrity

Target: Before Depot is relied upon for relevant German business records/processes.

## Record integrity

- [ ] Classify business objects by mutability and retention requirements.
- [ ] Make posted/finalized records immutable where required.
- [ ] Use explicit cancellation, reversal, correction, return, or credit transactions instead of destructive edits.
- [ ] Preserve links between original and correcting transactions.
- [ ] Preserve historical values needed to understand a transaction later.
- [ ] Prevent silent renumbering or reuse of finalized document numbers.
- [ ] Define numbering rules for invoices, credit notes, shipments, purchase documents, and other relevant records.

## Traceability

- [ ] Ensure relevant business events can be reconstructed chronologically.
- [ ] Preserve actor and timestamp information.
- [ ] Record workflow status transitions.
- [ ] Ensure audit and business transactions commit consistently.
- [ ] Define correction reasons where appropriate.

## Retention and export

- [ ] Define retention categories without hard-coding legal periods where deployment policy should control them.
- [ ] Provide machine-readable export of relevant records and metadata.
- [ ] Preserve readability of retained documents.
- [ ] Ensure backup/restore does not break historical integrity.

## Documentation

- [ ] Create technical input for a GoBD-oriented procedural documentation package.
- [ ] Document data creation, processing, storage, correction, export, backup, restore, and migration.
- [ ] Maintain version/migration history sufficient to explain historical data states.

# Phase 7 - Software quality and accessibility

Target: 1.0 and continuous improvement.

## ISO/IEC 25010 inspired quality gates

- [ ] Functional suitability: critical workflows have acceptance tests.
- [ ] Performance efficiency: complete 100,000+ record tests and define measurable limits.
- [ ] Compatibility: test supported Windows and database versions.
- [ ] Interaction capability: verify consistent UX and error/empty/loading states.
- [ ] Reliability: test recovery, interruption, concurrency, and failure modes.
- [ ] Security: include security checks in release acceptance.
- [ ] Maintainability: enforce architecture and coding standards.
- [ ] Flexibility: validate supported deployment/database configurations.
- [ ] Safety: prevent workflows that can silently corrupt or misrepresent business state.

## Accessibility

- [ ] Establish WCAG 2.2 AA / EN 301 549 inspired desktop UI requirements where applicable.
- [ ] Verify keyboard-only operation.
- [ ] Verify focus order and visible focus.
- [ ] Verify accessible names and automation properties.
- [ ] Verify contrast.
- [ ] Verify screen-reader basics.
- [ ] Verify 100%, 125%, 150%, and 200% scaling.
- [ ] Ensure status/error information is not communicated by color alone.

# Release security gate

A production release should not be approved until at least the following evidence exists:

- [ ] Release build and automated tests pass.
- [ ] Security-relevant tests pass.
- [ ] No unresolved critical vulnerability exists in shipped dependencies or code.
- [ ] High vulnerabilities are remediated or explicitly documented and risk-accepted.
- [ ] SBOM generated.
- [ ] Dependency/license review completed.
- [ ] Executable/package signing verified.
- [ ] Upgrade and rollback tested.
- [ ] Backup and restore tested for supported deployment paths.
- [ ] Release notes include security-relevant changes and known limitations where appropriate.
- [ ] Compliance documentation affected by the release has been reviewed.

# Suggested implementation order

1. Documentation skeleton and ownership. **Complete**
2. SBOM and dependency/CVE scanning in CI. **Complete**
3. Threat model and security architecture review. **Baseline complete; remediation continues in Phase 2+**
4. First-run administrator and credential-storage hardening.
5. Audit-log completion and retention/export policy.
6. Release signing and release provenance.
7. GDPR data inventory/retention model.
8. GoBD-oriented immutable business-record model.
9. CRA risk assessment and vulnerability/update lifecycle.
10. E-invoicing conformance when structured invoicing enters scope.
11. Enterprise identity/SIEM features based on customer demand.

## Review cadence

Review this roadmap at least:

- before every major/minor production release,
- after material architecture or deployment changes,
- after significant security incidents or vulnerability discoveries,
- when relevant legislation or standards change.
