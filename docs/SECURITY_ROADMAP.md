# Depot Security and Compliance Roadmap

## Purpose

This roadmap defines the security, privacy, regulatory, and software-assurance work required to move Depot from a preview application toward a production-ready inventory and business operations platform.

The roadmap is guidance for engineering and release planning. It does not by itself establish legal compliance or certification.

## Objectives

Depot should be developed toward alignment with the following areas where applicable:

- EU Cyber Resilience Act (CRA)
- GDPR / DSGVO
- German GoBD requirements for relevant business records and processes
- EN 16931 based electronic invoicing where invoice exchange is implemented
- ISO/IEC 27001 compatible security controls
- ISO/IEC 27034 application-security practices
- ISO/IEC 25010 software quality characteristics
- OWASP secure-development guidance, including ASVS/SAMM where applicable
- WCAG 2.2 AA / EN 301 549 accessibility principles
- enterprise customer requirements influenced by NIS2 and supply-chain security

## Guiding principles

1. Security by design and by default.
2. Least privilege for users, services, and database identities.
3. Business records become immutable when their workflow requires historical integrity.
4. Corrections use traceable reversal/correction transactions rather than destructive edits.
5. Security-relevant actions are auditable.
6. Secrets and credentials are never written to logs or exported unintentionally.
7. Every production release has a traceable source, dependency set, build, and security status.
8. Vulnerabilities have an owner, severity, remediation target, and disclosure process.
9. Backup is not considered complete without tested recovery.
10. Compliance evidence should be generated by normal engineering processes wherever possible.

# Phase 2 - Security hardening

**Status: TECHNICAL IMPLEMENTATION COMPLETE — 2026-08-22**

Target: Before release candidate.

The application and CI controls that can be implemented without production infrastructure are complete. Items intentionally left open below are release/deployment acceptance gates requiring a production signing identity, real provider instances, or real operating-system permission boundaries. They must be completed before the affected production configuration is declared supported.

## Authentication and authorization

- [x] Remove the production default administrator password workflow.
- [x] Require administrator creation or secure credential initialization on first production start.
- [x] Enforce an appropriate password policy.
- [x] Review and harden PBKDF2 parameters; new hashes use PBKDF2-HMAC-SHA256 with an increased work factor while the versioned format preserves compatibility.
- [x] Rate-limit/temporarily throttle repeated authentication failures per account.
- [x] Verify authorization at service/business boundaries, not only in the UI.
- [x] Test role union, privilege escalation, administrator override, and creator/approver separation.
- [x] Evaluate MFA and external identity-provider support: retain local authentication for the current desktop release; track MFA and Entra ID/OIDC/SAML as post-1.0 enterprise capabilities in Phase 8.

## Secrets and configuration

- [x] Protect database credentials and other persisted connection secrets at rest using Windows DPAPI `CurrentUser` protection.
- [x] Define Windows-user/machine behavior for protected configuration in `docs/compliance/SECURE_CONFIGURATION.md`.
- [x] Ensure secrets are redacted from audit presentation/diagnostics and define redaction requirements for future logs, telemetry, exports, and crash information.
- [x] Document secure configuration for SQL Server, MySQL, and MariaDB.
- [x] Document database least-privilege requirements.
- [x] Require encrypted database transport for remote providers; SQL Server encryption and MySQL/MariaDB TLS cannot be disabled through supported settings.

## Audit and logging

- [x] Complete the dedicated audit-log viewer with filters, paging, sanitized detail comparison, and CSV export.
- [x] Define security-event categories in `docs/compliance/AUDIT_AND_RECOVERY.md` and `SECURITY_LOGGING.md`.
- [x] Define audit retention and export behavior.
- [x] Protect audit records from normal application modification/deletion; direct database modification is documented as privileged break-glass activity.
- [x] Record administrator overrides with actor, UTC timestamp, affected object, and an explicit/default override reason.
- [x] Define UTC clock/time-zone handling for audit evidence.
- [x] Review logging/audit presentation for personal data, credentials, connection strings, tokens, keys, hashes, and other sensitive values.

## Backup and recovery

- [x] Define and implement automatic backup retention: preserve at least the ten newest automatic backups and remove additional automatic backups only after 30 days.
- [x] Define backup access-control requirements.
- [x] Evaluate backup encryption. Built-in archive encryption is deferred until a managed key-store design exists; production backup storage must use OS/storage encryption and ACLs in the interim.
- [ ] Complete the real insufficient-permission recovery scenario. Clean/corrupt/interrupted/unavailable-target behavior has automated regression coverage; ACL denial requires a real Windows permission boundary.
- [ ] Perform and record recovery drills for every production-supported database provider. SQLite has automated baseline evidence; SQL Server and MySQL/MariaDB require configured provider instances.
- [x] Document recovery objectives, acceptance criteria, and operational recovery procedure in `docs/compliance/AUDIT_AND_RECOVERY.md`.

## Release integrity

- [ ] Authenticode-sign production executables and installer/packages with the production certificate. CI signing support is implemented; completion requires the production signing identity.
- [ ] Validate production timestamping with the real signing certificate. Timestamp support is implemented in the release workflow.
- [x] Protect signing credentials outside the source repository; the workflow consumes protected GitHub secrets and contains no certificate/private key.
- [x] Ensure CI release artifacts correspond to the exact source/tag revision.
- [x] Publish SHA-256 hashes for release artifacts where appropriate.

# Phase 3 - GDPR / data protection readiness

**Status: TECHNICAL IMPLEMENTATION COMPLETE — 2026-08-22**

Target: Before production use with personal data.

The technical privacy baseline is implemented. Depot intentionally does not hard-code legal bases, statutory retention periods, erasure decisions, or controller obligations; these remain deployment/legal decisions and must be validated before production use.

- [x] Inventory personal-data categories processed by Depot in `docs/compliance/DATA_INVENTORY.md`.
- [x] Document purposes and typical data flows, including derived PDF/export/backup copies.
- [x] Identify storage locations including databases, protected settings, diagnostics/logs, backups, PDFs, spreadsheet/CSV exports, notifications, and generated documents.
- [x] Apply a technical data-minimization baseline through purpose-based fields, field-length/normalization validation, RBAC, secret redaction, and privacy review rules.
- [x] Define retention and deletion behavior by record category in `docs/compliance/RETENTION_POLICY.md`; concrete legal periods remain controller/deployment policy.
- [x] Distinguish delete, deactivate, anonymize, archive, and legally/business-retained records and prohibit unsafe blanket deletion of historical business/audit evidence.
- [x] Provide an administrator workflow under Administration → Privacy Data to locate personal data across users, customers, customer contacts, suppliers, and attributable audit records.
- [x] Provide an administrator-only machine-readable JSON discovery export for data-subject handling; authentication hashes and connection secrets are excluded by design.
- [x] Align backup retention with lifecycle policy and document that restoring historical backups can reintroduce previously removed data and requires reapplication of applicable erasure/restriction actions.
- [x] Document privacy-by-design review requirements for new personal-data features in `docs/compliance/PRIVACY_BY_DESIGN.md`.
- [x] Establish a default-deny review gate for future telemetry, analytics, crash upload, cloud sync, remote support, or other background external transmission in `docs/compliance/TELEMETRY_POLICY.md` and the PR review process.

# Phase 4 - GoBD and business-record integrity

**Status: TECHNICAL IMPLEMENTATION COMPLETE — 2026-08-22**

Target: Before Depot is relied upon for relevant German business records/processes.

The technical business-record integrity baseline is implemented. Deployment-specific tax relevance, statutory retention periods, organizational procedures, formal procedural-documentation approval, external-system responsibilities, and tax-authority-specific export requirements remain acceptance gates outside the generic application code.

## Record integrity

- [x] Classify business objects by mutability and retention requirements using `BusinessRecordCatalog`.
- [x] Make posted/finalized records immutable through service/repository workflow-state and optimistic-concurrency predicates in the reviewed core workflows.
- [x] Use explicit cancellation, reversal, correction, return, close, or credit transactions instead of destructive edits.
- [x] Preserve original records and links/references needed to reconstruct correcting transactions.
- [x] Preserve historical before/after values in audit evidence for audited retained state changes.
- [x] Prevent silent renumbering or reuse through stable identity-derived document numbers and documented no-reuse/no-backfill rules.
- [x] Define numbering rules for invoices, credit notes, shipments, purchasing, warehouse, return, and sales documents in `docs/compliance/BUSINESS_RECORD_INTEGRITY.md`.

## Traceability

- [x] Ensure relevant audited business events can be reconstructed chronologically through UTC audit history and structured snapshots.
- [x] Preserve actor and timestamp information for attributed workflow transitions.
- [x] Record workflow status transitions through versioned business state and audit entries.
- [x] Ensure reviewed retained business mutations and corresponding audit entries commit consistently in shared database transactions; sales-order draft save was hardened to the same model.
- [x] Define and require correction reasons in reviewed reversal/cancellation/credit workflows where needed to explain the correction.

## Retention and export

- [x] Define technical retention categories without hard-coding statutory periods that belong to deployment/legal policy.
- [x] Provide machine-readable JSON business-record evidence export with record classification, chronological audit events, actor/timestamps, sanitized before/after data, and latest snapshot.
- [x] Preserve readability through structured authoritative data and documented reconstruction/export semantics.
- [x] Define backup/restore integrity rules so identities, document numbers, relationships, status, audit history, and schema version are preserved as a unit.

## Documentation

- [x] Create technical input for a GoBD-oriented procedural documentation package in `docs/compliance/PROCEDURAL_DOCUMENTATION.md`.
- [x] Document data creation, processing, storage, correction, export, backup, restore, and migration.
- [x] Define migration/change-control rules to preserve stable ids, permanent document numbers, audit history, semantic meaning, and explainable historical states.

# Release security gate

A production release should not be approved until at least the following evidence exists:

- [ ] Release build and automated tests pass.
- [ ] Security-relevant tests pass.
- [ ] No unresolved critical vulnerability exists in shipped dependencies or code.
- [ ] High vulnerabilities are remediated or explicitly documented and risk-accepted.
- [ ] SBOM generated.
- [ ] Dependency/license review completed.
- [ ] Executable/package signing verified.
- [ ] Upgrade and rollback tested.
- [ ] Backup and restore tested for supported deployment paths.
- [ ] Release notes include security-relevant changes and known limitations where appropriate.
- [ ] Compliance documentation affected by the release has been reviewed.
